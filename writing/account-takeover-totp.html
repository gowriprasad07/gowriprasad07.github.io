Account takeover through an unthrottled TOTP check

This is the kind of bug that makes two-factor authentication worse than useless, because it gives everyone a false sense of safety while quietly handing out accounts. A product I was testing had TOTP as a second factor, the six-digit code from an authenticator app. The verification step for that code had no rate limiting, and the way it was wired let me chain two requests into a full account takeover, admin included. Nothing exotic, just two common mistakes lined up in a row.

How the login was meant to work

Two factors, in sequence. You send a username and password, and if TOTP is enabled, the app then asks for the six-digit code. You post the username and the code to a verification endpoint. If the code checks out, the app hands back a short-lived value, call it a "cookie code," which you then exchange at a token endpoint for a real access token. The access token is what actually logs you in and authorises your API calls.

So the flow is: verify TOTP, get a cookie code, swap the cookie code for an access token. On paper that's fine. The problem is in the gaps between those steps.

Mistake one: no rate limiting on the code check

The TOTP verification request looked roughly like this: 

POST /authorization/totp_verification/

username=admin&totp=112959

A TOTP code is six digits. That's a million possibilities, which sounds like a lot until you realise the endpoint accepted attempt after attempt with no throttling, no lockout, no delay. A million tries with no brake is not a million tries, it's a script running for a while. And because the code rotates on a fixed window, you don't even need the whole space; you need to land a valid code inside its lifetime, which a fast unthrottled loop can do.

Rate limiting is the entire security model of a six-digit code. Six digits is deliberately small so a human can type it, and the only reason that's acceptable is that you're supposed to get a handful of guesses before the door locks. Remove the lock and the short code stops being a second factor and becomes a speed bump.

Mistake two: the code was all you needed

Here's the part that turned a brute-force into a takeover. The verification endpoint took a username and a code. It didn't require anything that proved you'd passed the first factor for that user, no bound secret tied to a successful password step. So I could put any username in, admin included, and just brute-force the code for it directly.

When the code finally matched, the response handed back the cookie code for that account: 

{
  "user_type": "existing_user",
  "code": "<a cookie code, valid for this account>"
}

Then the second request, exactly as a normal client would do it, exchanges that cookie code for an access token: 

POST /oauth2/token/

grant_type=client_credentials
(cookie code carried as the credential)

And the response is a live token for the account: 

{
  "access_token": "<valid token for the targeted user>",
  "expires_in": 1800,
  "token_type": "Bearer",
  "scope": "read write"
}
The TOTP step verified the code but never verified that you were the person the code belonged to. Guessing six digits for a username you chose was the whole authentication.

Putting it together

Two requests, start to finish. Point the TOTP endpoint at a username, brute-force the six-digit code with no throttling to stop you, take the cookie code from the success response, and swap it for an access token. At the end you hold a valid Bearer token for any account you named, with read and write scope. Choose admin and you own the product.

That's why this is a High. No prior access, no phishing, no social step. Pick a target username, run the loop, log in as them.

The fix

Both mistakes need closing, and they close in different places.

Rate-limit the verification endpoint. A small number of failed TOTP attempts should lock the flow, exactly like a password. This alone turns a certain brute-force back into a lottery you'll almost never win inside a code's lifetime.

Bind the TOTP step to the first factor. The code check should only succeed for a user who has just proven the first factor, by carrying a unique, server-issued value tied to that specific successful login rather than trusting a username the client typed in. Then you can't walk up to the second factor for an arbitrary account and start guessing; you have to have passed the first factor for that exact user first. That's the change that actually restores what two-factor is supposed to mean.

What to take from it

Whenever I see a numeric verification step now, OTP, TOTP, an SMS code, I ask the same two questions before anything else. Is it rate limited, and is it bound to the earlier step, or can I request it for any account I like? Either gap on its own is a finding. Both together, as here, is an account takeover. A second factor is only a second factor if the first one still has to happen.
