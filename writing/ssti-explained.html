How server-side template injection actually works

For a long time I copied SSTI payloads without understanding them. I knew {{7*7}} returning 49 meant something was wrong, and I knew the longer payloads sometimes gave me command execution. I did not know why. It turns out the whole thing is one language feature, used in a place it was never meant to reach.

Templates evaluate expressions

A template engine takes a document with placeholders and fills them in. In Jinja2, the Python engine behind Flask, a template looks like this: 

<h1>Hello {{ user.name }}</h1>

At render time the engine evaluates user.name as an expression. That is the important word. It is not doing string substitution from a lookup table; it is resolving an attribute on a live Python object, the same way your own code would.

Where it goes wrong

Normally the template is a file written by a developer and the untrusted input is only the data passed into it. That is safe. The bug appears when user input becomes part of the template itself: 

render_template_string("<p>Hi " + name + "</p>")

Now an attacker controls the expression source, not just the values. Anything the engine can evaluate, they can evaluate.

Why the long payloads look the way they do

Once you can evaluate expressions, the goal is to reach something dangerous. Python objects expose their own internals as attributes, so you can walk from a harmless value to the wider runtime by chaining lookups: 

{{ ''.__class__ }}          → the str class
{{ ''.__class__.__mro__ }}   → its ancestry, including object
{{ ''.__class__.__mro__[1].__subclasses__() }}
                             → every class loaded in the process

That last list is where the interesting things live. Somewhere in it is a class that can open files or spawn a process, and from there it is ordinary Python.

The payload is not an exploit string. It is a path through the object graph.

What I took away as a tester

Grep for template rendering that takes a dynamic string rather than a filename. Anywhere user input reaches the template source instead of the template context, you have a candidate. Sandboxed environments raise the bar but have historically been escapable, so treat them as a mitigation rather than a fix.

And the reason I finally understood it: I wrote a Jinja2 template myself and watched it resolve an attribute on an object I had defined. The payloads stopped being incantations.
