DC-9: SQL injection, a hidden knock, and a sudo write to root

This Linux box has a bit of everything, and the steps hand off to each other nicely. A SQL injection gives me a pile of credentials, a file read points at a hidden way in, a port knock actually opens that way, and a single sudo rule at the end turns a normal user into root. None of it is hard on its own, but you have to spot each clue and follow it to the next.

SQL injection in the search

The site is a staff directory with a search page. The search was injectable, so I used a UNION-based injection to read straight out of the database. It exposed two databases worth of data: a Staff table and a users table.

The Staff table had the display records. The users table was the interesting one, it held usernames and password hashes for the actual site accounts. I pulled all of them and cracked what I could. Now I had a set of real credentials.

Logging in and finding an LFI

Logging into the site as admin unlocked an "Add Record" and a manage.php page. The manage page took a file parameter, and that's a classic tell. I tried a path traversal and it read local files back to me: 

manage.php?file=../../../../../../etc/passwd

So I had local file inclusion. Reading /etc/passwd gave me the list of real users on the box (fredf, janitor, and others), which lines up with names I'd want to try over SSH. But SSH wasn't open. That's where the next clue came in.

A hidden port knock

Since I could read arbitrary files, I went looking for config that might explain the closed SSH port. Reading the knock daemon's config was the win: 

manage.php?file=../../../../../../etc/knockd.conf

Port knocking is a little trick where a port (here, SSH) stays firewalled off until you connect to a specific sequence of ports in the right order. Hit those ports in sequence and the firewall opens SSH just for you. The config handed me the exact sequence: 

openSSH  sequence = 7469, 8475, 9842

I knocked those three ports in order, and SSH opened up. Then I logged in as one of the users whose password I'd cracked earlier (fredf). Foothold on the box.

The path to root

First thing on any Linux box: sudo -l. It showed fredf could run one specific binary as root with no password: 

User fredf may run the following commands on dc-9:
    (root) NOPASSWD: /opt/devstuff/dist/test/test

That test program took an input file and an output file and wrote the input's contents into the output, running as root. A root-owned write-anywhere primitive is all you need. The cleanest target is /etc/passwd: add a line for a brand-new user with a known password and a UID of 0, and you've created a second root account. 

# make a passwd line with a known password and uid 0
echo 'zombie:$1$...hash...:0:0:root:/root:/bin/bash' > /tmp/zombie

# use the root-owned tool to append it to /etc/passwd
sudo ./test /tmp/zombie /etc/passwd

# become the new root user
su zombie

After that, su zombie dropped me into a root shell, and the flag was sitting in /root. The box printed a big "NICE WORK" banner, which is always a nice way to finish.

The chain, in one line

SQLi dumps the user hashes, cracking gives real logins, LFI reads the knockd config, knocking opens SSH, and a passwordless sudo write to /etc/passwd creates a second root.

What I took from it

Two habits this box reinforced. When you get a file read, don't stop at /etc/passwd, read the service configs too, because that's where the box hides how it's actually wired (the knock sequence would have been impossible to guess). And when you land a shell, sudo -l is always the first thing to run. A single NOPASSWD rule on the wrong binary is one of the most common ways a normal user becomes root, and it's a real-world finding, not just a CTF trick.
