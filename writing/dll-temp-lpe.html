A SYSTEM service that loaded a DLL from a world-writable folder

This one is a classic Windows privilege escalation, and it's a good example because the bug isn't in the code doing anything clever, it's in where the code loads a file from. A security service running as SYSTEM loaded a DLL out of a folder any user can write to. That's all it takes. A normal low-privileged user could drop their own DLL in that folder and have it run as SYSTEM on the next reboot.

What the service did

On startup, the service wrote a helper DLL into C:\Windows\Temp and then loaded it into its own process. That process runs as NT AUTHORITY\SYSTEM, the highest privilege on the machine.

The problem is the location. C:\Windows\Temp is world-writable, any user on the box can create and modify files there. So the service was loading executable code from a place that an unprivileged attacker fully controls. Loading a DLL means running whatever code is inside it, so if I can choose the DLL, I can run my code inside a SYSTEM process.

The detail that made it reliable

There's a wrinkle that makes this cleaner than it first looks. The service writes the DLL itself on startup, so you might think it would just overwrite anything an attacker placed there. Two things defeat that.

First, after loading the DLL successfully, the service deletes it from the temp folder. That leaves the path free for any local user to recreate before the next start.

Second, and this is the key, if a file is already sitting at that path and it's marked read-only, the service's attempt to write its own DLL fails, but it carries on and loads the existing file anyway. So the attack is simply: drop your DLL there, mark it read-only, and wait for the service to start. 

# as a normal user
attrib +R evil.dll
copy evil.dll C:\Windows\Temp\   (preserving the read-only flag)
# reboot, the service loads evil.dll as SYSTEM

The root cause

The service never checked the DLL it was about to load: not where it came from, not who could write to that folder, not whether the file was signed, not whether its own write even succeeded. It just called the standard load function on a path in a world-writable directory and trusted whatever was there.

A SYSTEM process is only as trustworthy as the files it loads. Load one from a folder every user can write to, and you've handed every user SYSTEM.

Notably, the codebase already had a safe loader that verified a DLL's signature and path before loading it. This one spot just called the raw load function directly and skipped all of that. A single unchecked load, in a service that otherwise did it properly.

The fix

Never load executable code from %windir%\Temp or any user-writable path. Keep the DLL in a protected directory (under Program Files or ProgramData) where only SYSTEM and Administrators can write and normal users can only read. If a staging folder is genuinely needed, create a service-owned private one at install time with permissions that deny users write access. And validate before loading, check the signature and the expected path, which is exactly what the codebase's safe loader already did.

What to take from it

When I look at a Windows service now, two questions come first: what does it run as, and what does it load, and from where. A high-privilege process that reads a config, a DLL, a script, or an executable out of a location a normal user can write to is a privilege escalation waiting to happen. The permissions on the folder matter as much as the code. This kind of bug is quiet, it doesn't crash anything or look wrong in testing, but it hands a standard user the whole machine.
